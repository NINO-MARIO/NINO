# คู่มือพนักงาน: มิ้ม (Local AI ในแอป NINO)

มิ้มคือระบบตอบคำถามภาษาไทยที่ทำงานในเครื่อง รวมเข้ากับแอป NINO เป็นป็อปอัพอีกหนึ่งโหมดข้างปุ่ม Code และ Roleplay
โค้ดเครื่องยนต์ย้ายมาจากโปรเจกต์ NINO Local AI ทั้งชุด (ดูส่วนที่ 1 ถึง 12 ท้ายเอกสารนี้)

## ★ สรุปสำคัญ (อ่านก่อนแก้ทุกครั้ง)

★ 1. ทุกรอบที่ทำเสร็จ ต้องส่ง NINO.zip ที่เป็นเวอร์ชันล่าสุดกลับมาเสมอ เป็นซิปทั้งโปรเจกต์ที่แก้แล้ว ไม่ใช่แค่ไฟล์ที่แก้ ห้ามจบรอบโดยไม่มีซิปล่าสุด

★ 2. ห้ามทำให้ NINO.zip ถอยหลัง ก่อนส่งทุกครั้งต้องรัน `bash tools/verify-all.sh` ในโฟลเดอร์ที่แก้แล้ว และเทียบกับผลก่อนแก้ ขั้นตอนไหนที่เคยผ่านต้องยังผ่าน จะรายงานว่า "ผ่านทั้งหมด" ได้ก็ต่อเมื่อเห็นผลจริงเท่านั้น

★ 3. มิ้มชั้นแรกตอบจากกฎและความรู้ที่ผู้ใช้สอนเท่านั้น (ไม่ใช้โมเดล) ชั้นที่สองคือโมเดลในเครื่อง Q2_K มีสองโหมด: โหมด 1 (รวมกับมิ้ม) ใช้เฉพาะเมื่อผู้ใช้เลือกเอง และใช้ได้เฉพาะคำที่มิ้มตอบไม่ได้ โดยโมเดลต้องตอบจากความรู้ของมิ้มที่ยกมาให้ และคำตอบต้องผ่านการตรวจ (ดูข้อ 44) โหมด 2 (ปกติ) เป็นค่าเริ่มต้น ใช้แทน API เฉพาะแชตโค้ดและโรลเพลย์ที่ส่ง localOk มาเอง งานเสริม (ตั้งชื่อหัวข้อ สรุปโน้ต ข้อความวนซ้ำ) ไม่ใช้โมเดลในเครื่อง ชั้นที่สามคือ API ออนไลน์ (แชตโค้ดและโรลเพลย์ที่มีคีย์) มิ้มเองไม่เรียก API ยกเว้นพี่นาเดียร์ที่ผู้ใช้เปิดเองและยืนยันทุกครั้ง พี่นาเดียร์ส่งความรู้ของมิ้มไปด้วย ซึ่งขัดกับคำอธิบายว่า API ไม่รวมกับมิ้ม จึงรอการตัดสินใจของผู้ใช้ (ดูข้อ 45) พี่นาเดียร์ส่งคำถามผ่านฟังก์ชัน geminiGenerate พร้อม noLocal เสมอ ห้ามเพิ่มการเรียกเครือข่ายเข้า mim/ (เช่น fetch ตรง) โดยไม่ได้รับอนุมัติ การดาวน์โหลดโมเดลทำใน js/local-llm.js เท่านั้น

★ 4. ห้ามเดาเพื่อให้ดูฉลาด เมื่อไม่มีหลักฐานในความรู้ ต้องตอบแบบ fallback ว่าไม่รู้ และเชิญให้สอน การตอบว่ารู้ทั้งที่ไม่รู้เป็นข้อบกพร่องร้ายแรงที่สุดของระบบนี้

★ 5. คีย์ localStorage ของความรู้ต้องคงชื่อเดิม ได้แก่ `nino_local_ai_kb_v1`, `nino_local_ai_set_v1`, `nino_local_ai_mind_v1` การเปลี่ยนชื่อคีย์จะทำให้ความรู้ที่ผู้ใช้สอนไว้หายทั้งหมด สิ่งที่เปลี่ยนได้คือข้อความที่แสดงบนจอ (ตอนนี้แสดงว่า "มิ้ม")

★ 6. ห้ามมีอิโมจิ ทั้งในโค้ด ข้อความบนจอ และคำตอบของมิ้ม เครื่องยนต์กรองชั้นหนึ่งด้วย Text.stripEmoji และ js/no-emoji.js กรองอีกชั้นในแอป

★ 7. คำตอบของมิ้มต้องเป็นภาษาไทยล้วน

★ 8. ไฟล์ที่ล็อกของ NINO (เช่น service-worker.js, tools/check.js, tools/make-now.js, tools/test/*, .github/, android/, js/native-bridge.js) ห้ามแก้เองโดยไม่ได้รับอนุมัติจากผู้ใช้ ดูรายการเต็มในส่วน [ล็อก] ของ NOW.md

★ 9. service-worker.js ได้รับอนุมัติให้แก้แล้ว สคริปต์ของมิ้มถูกแคชล่วงหน้าอัตโนมัติจากแท็ก script ใน index.html ส่วน mim/mim.css เพิ่มเข้า BASE_ASSETS ตรวจการออฟไลน์จริงบนเครื่องยังไม่ได้ทำ ต้องทดสอบหลังติดตั้งเว็บ

★ 10. ความรู้เริ่มต้นเติมเพียงครั้งเดียวตอนเปิดครั้งแรก ผู้ใช้ที่เคยเปิดระบบเดิมแล้วจะยังเห็นคำตอบเก่าที่เขียนว่า "NINO" จนกว่าจะลบหรือสอนใหม่ ห้ามแก้ด้วยการเขียนทับคีย์ความรู้โดยไม่บอกผู้ใช้

★ 11. งบความเร็ว "สร้างกราฟทั้งชุด 5000 รายการ" (400 มิลลิวินาที) ยังไม่ผ่าน ค่าที่วัดได้ผันผวนมากบนเครื่องทดสอบ 2 คอร์ การจะผ่านงบต้องเปลี่ยนการออกแบบ ไม่ใช่ปรับงบ

★ 12. ห้ามแก้โค้ดของ Code และ Roleplay เพื่อให้มิ้มทำงาน การเชื่อมมีจุดเดียวคือปุ่ม mode-mim ใน index.html และการผูกคลิกใน app.js ถ้าต้องแก้แกนของ Code หรือ Roleplay ให้ทดสอบทั้งสองโหมดก่อนส่งทุกครั้ง ตามกติกาของ HANDOFF

★ 13. ห้ามลบ `stopPropagation` ที่ราก `#mim-root` ใน mim/mim.js ถ้าลบ การพิมพ์ในมิ้มจะทะลุไปถึงทางลัดแบบ document ของแชตหลัก เช่น Ctrl+F, Ctrl+K และ Escape ทดสอบด้วยตัวนับ keydown ที่ document ใน mim/tests/mim-popup.test.js

★ 14. พี่นาเดียร์ต้องเปิดเองด้วยการกดปุ่มและยืนยันกล่องถามเท่านั้น ส่งคำถามเฉพาะตอนผู้ใช้พิมพ์ถาม ไม่มีการส่งอัตโนมัติ และใช้เฉพาะ API ที่ผู้ใช้ตั้งไว้ในแอป ถ้า API ใช้ไม่ได้หรือคำตอบไม่ใช่ภาษาไทย ต้องกลับไปใช้มิ้มออฟไลน์และแจ้งผู้ใช้ ห้ามเงียบๆ

★ 15. คำตอบจากพี่นาเดียร์ต้องติดป้าย "ยังไม่ยืนยัน" และเข้าคลังความรู้ออฟไลน์ก็ต่อเมื่อผู้ใช้กดปุ่ม "จำคำตอบนี้" เองเท่านั้น ห้ามจำอัตโนมัติ เพราะคำตอบจากโมเดลอาจผิด และคลังความรู้ที่ผิดจะส่งต่อไปยังการตอบออฟไลน์ทุกครั้ง

★ 16. ก่อนยอมรับการแก้ มิ้มต้องผ่านชุดทดสอบทั้งสามชุด (engine-tests, nadia-test และ mim-popup) ทั้งใน tools/verify-all.sh และในขั้นตอน NINO unpack zip (android/ci/unpack-zip.yml) ซึ่งจะไม่ commit ถ้าไม่ผ่าน ไฟล์ .github/workflows ต้องอัปโหลดเองจากโฟลเดอร์ android/ci ทุกครั้งที่แก้ เพราะ unpack ข้ามโฟลเดอร์ .github

★ 17. ห้ามเดาจากคำที่รู้จักบางส่วน ถ้าคำถามมีคำเนื้อหาที่ยังไม่รู้จัก (ไม่นับคำขอทั่วไปอย่าง เล่า/ฟัง/บอก/หน่อย/เลย และคำลงท้ายล้วนอย่าง เหรอ/อ่ะ/นะ/คะ) มิ้มต้องขอให้สอน จะตอบจากการจับคู่คล้าย การกระตุ้นความหมาย หรือการเรียบเรียงไม่ได้ การจับคู่คล้ายใช้ได้เฉพาะเมื่อคำที่ไม่รู้จักเป็นการพิมพ์ผิดหนึ่งตัวอักษรของคำที่รู้จัก (ดู hard และ typoOnly ใน 37-thinker.js) ทดสอบด้วย "ดาวอังคารมีกี่ดวง" ใน mim/tests/learn-test.js
★ 17.1 กำกวมไม่ตอบ: ถ้าผู้สมัครอันดับหนึ่งชนะอันดับสองของการกระตุ้นความหมายไม่ถึง 0.1 (ค่า ambiguousMargin) มิ้มจะไม่ตอบจากการกระตุ้นนั้น เพราะคำทั่วไปอย่าง "วัน" หรือ "มิ้ม" ทำให้หลายเรื่องคะแนนใกล้กัน ผลวัดใน mim/tests/eval-retrieval.js (--gate) กันการตอบผิดไม่ให้เพิ่ม
★ 17.2 เส้นทางความหมาย: รายการที่ใช้ตอบจากเส้นทางต้องมีคำเฉพาะของคำถาม (คำที่อยู่ในความรู้ไม่เกิน 2 รายการ) อย่างน้อยหนึ่งคำ กันการตอบจากคำทั่วไปที่พาเส้นทางไปเรื่องอื่น ยังมีข้อผิดที่รู้แล้วหนึ่งข้อ: "สงกรานต์คือวันไหนของปี" อาจได้ "หนึ่งปีมี 12 เดือน" จึงตั้งเพดานผลผิดของชุด HELD ไว้ที่ 1 และรายงานใน eval-retrieval.js

★ 18. การเรียนรู้จากการสอนมีสามกติกา ก) สอนหนึ่งครั้งขยายรูปคำถามได้สูงสุด 4 รูป แต่ไม่เขียนทับความรู้เดิมที่มีคำถามรูปนั้นอยู่แล้ว ข) การอัปเดตคำตอบเดิมไม่สร้างรูปเพิ่ม ค) ชุดความรู้เริ่มต้น (pack) เติมเฉพาะคำถามที่ยังไม่มีและบันทึกรุ่นไว้ ห้ามเติมทับของผู้ใช้

★ 19. ผู้เรียบเรียง (47-compose.js) สร้างประโยคใหม่ได้เฉพาะจากคำตอบที่มีหัวเรื่องเดียวกัน หัวเรื่องต้องไม่ใช่คำทั่วไป และต้องจบด้วยคำลงท้าย ไม่ซ้ำคำตอบเดิม และติดป้ายทดลองเสมอ ห้ามจำผลของผู้เรียบเรียงเข้าคลังเอง

★ 20. ชื่อที่แสดงของระบบคือ "มิ้ม" ทุกที่ที่ระบบพูดถึงตัวเอง ใช้ displayName ตอนแสดงผลเท่านั้น ไม่แก้ข้อมูลที่เก็บ ชื่อแอป NINO ในประโยคที่พูดถึงแอปต้องไม่ถูกเปลี่ยน

## โครงสร้างในโฟลเดอร์ mim/

- `mim/engine/` เครื่องยนต์ 17 ไฟล์ โหลดตามลำดับใน index.html (00-core ถึง 50-chat) ไฟล์เหล่านี้กำหนด `window.NINO` ภายในแอป ชื่อนี้สงวนไว้ให้เครื่องยนต์ ไม่ใช่ชื่อแอป
- `mim/mim.js` ตัวควบคุมป็อปอัพ สร้างกล่องตอนเปิดครั้งแรก เริ่มเครื่องยนต์ตอนเปิดครั้งแรกเช่นกัน แสดงข้อความด้วยคลาสชุดเดียวกับแชตหลักเพื่อให้กลมกลืน
- `mim/mim.css` สไตล์หน้าต่างเรโท ใช้ฟอนต์ Pixelify Sans กับ Chakra Petch ส่วนข้อความในแชตใช้ฟอนต์เดียวกับแอป
- `mim/tests/engine-tests.js` ชุดทดสอบเครื่องยนต์ 53 เคส (ย้ายมาจาก NINO Local AI)
- `mim/nadia.js` พี่นาเดียร์: โหมดออนไลน์ที่ใช้ API ที่ผู้ใช้ตั้งไว้ในแอป ค้นความรู้ที่ใกล้คำถามแนบไปในคำสั่ง ไม่เก็บคีย์ API เอง
- `mim/engine/39-learn.js` การเรียนรู้จากการสอนครั้งเดียว (รูปคำถามใกล้เคียง) ชุดความรู้เริ่มต้น และชื่อที่แสดง
- `mim/engine/47-compose.js` ผู้เรียบเรียงประโยคใหม่จากคำตอบที่มีหัวเรื่องเดียวกัน ติดป้ายทดลอง
- `mim/data/pack-th.js` ชุดความรู้เริ่มต้นภาษาไทย (ข้อเท็จจริงที่ไม่เปลี่ยนตามเวลา) เพิ่มรายการได้โดยเพิ่มรุ่น
- `mim/tests/nadia-test.js` ทดสอบพี่นาเดียร์ 12 เคส ไม่ใช้เครือข่ายจริง ใช้ฟังก์ชันจำลอง
- `mim/tests/learn-test.js` ทดสอบการเรียนรู้ ผู้เรียบเรียง และกฎการไม่เดา 12 เคส
- `mim/tests/chat-session.js` บทสนทนาทดลองสำหรับอ่านด้วยตา ไม่ใช่การทดสอบผ่านหรือไม่ผ่าน
- `mim/tests/mim-popup.test.js` ทดสอบป็อปอัพในเบราว์เซอร์ 44 รายการ รวมนาเดียร์ ช่องสอนคำถาม/คำตอบ และปุ่มผิด ช่วยแก้
- `mim/MANUAL_TH.md` คู่มือนี้

การเชื่อมกับแอปมีสามจุด: ปุ่ม `mode-mim` ใน index.html, สคริปต์ที่โหลดท้าย index.html ก่อน app.js, และการผูกคลิกใน app.js ซึ่งเรียก `window.NINO_MIM.toggle()`

## การรันทดสอบ

- เครื่องยนต์: `node mim/tests/engine-tests.js`
- ป็อปอัพในเบราว์เซอร์: `NODE_PATH=<โฟลเดอร์ playwright> node mim/tests/mim-popup.test.js`
- ทั้งโปรเจกต์: `bash tools/verify-all.sh` (รวมทั้งสองชุดข้างต้นแล้ว)

## ขีดจำกัดที่ต้องบอกผู้ใช้ตรงๆ

- มิ้มตอบได้เฉพาะเรื่องที่มีในความรู้ที่สอนไว้ ไม่เข้าใจความหมายเชิงลึก และไม่สร้างประโยคใหม่เอง
- ความรู้เริ่มต้นมีไม่มาก คำถามที่ซับซ้อนมักตอบไม่ได้ และนั่นคือพฤติกรรมที่ถูกต้องตามกติกาข้อ 4
- โหนดบริบทช่วยเรื่องคำอ้างอิง เช่น "มันคืออะไร" แต่จะบอกชื่อเรื่องที่อ้างถึงทุกครั้ง เพื่อไม่ให้ผู้ใช้เข้าใจผิดว่าระบบรู้เรื่องใหม่
- พี่นาเดียร์ตอบได้ดีเท่ากับ API ที่ผู้ใช้เลือกไว้ และคุณภาพคำตอบไม่ได้มาจากเครื่องยนต์ของมิ้ม คำตอบจาก API ต้องตรวจเองก่อนจำ เครื่องยนต์ของมิ้มยังเป็นกฎและการค้นหาแบบคะแนนความคล้าย ไม่ได้เหนือกว่าโมเดลภาษาในด้านการเข้าใจความหมาย
- การตอบแบบออฟไลน์ของมิ้มมีเท่าที่ผู้ใช้สอน และไม่เปลี่ยนแปลงเมื่อเปิดนาเดียร์

# คู่มือเตือนตัวเอง: NINO Local AI

เอกสารนี้เขียนให้ผู้ช่วยที่รับช่วงงานต่อ (รวมถึงตัวฉันในรอบถัดไป) อ่านก่อนแตะโค้ดทุกครั้ง
ถ้าขัดกับความคิดของตัวเอง ให้ยึดเอกสารนี้

---

## 1. ฉันคือใครในโปรเจกต์นี้

ฉันคือพนักงานที่ถือเจตจำนงของเจ้าของโปรเจกต์ ไม่ใช่เครื่องมือที่รอคำสั่งทีละบรรทัด
งานคือทำให้ผลิตภัณฑ์นี้ใช้งานได้จริงระดับบริษัท ทุกการตัดสินใจต้องตอบสามข้อ:
ใช้งานจริงได้ไหม ต่อยอดได้ไหม และเจ้าของจะเชื่อถือผลลัพธ์นี้ได้ไหม
ถ้ามีจุดที่ไม่ชัด เลือกทางที่เป็นโปรดักชัน แล้วบอกเจ้าของสั้นๆ ว่าเลือกอะไรและเพราะอะไร

## 2. เจตจำนงของเจ้าของ (คำขอต้นฉบับ สรุป)

1. ต่อยอดจากความรู้และโค้ดที่เจ้าของเขียนไว้ ไม่ทิ้งของเดิม มองการณ์ไกลสำหรับอนาคต
2. ในที่สุดต้องมี LLM ภาษาไทยที่เป็นโมเดลจริง กินแรมไม่มาก และรวมมาในโปรเจกต์ได้
3. ระบบแตกเป็นไฟล์ย่อยและเชื่อมโหนดถึงกัน เก็บฐานโมเดลไว้ในโปรเจกต์
4. ผลลัพธ์ของโมเดลต้องเป็นภาษาไทยล้วน
5. เป้าหมายคือผลิตภัณฑ์ระดับบริษัท รูปแบบสมัยใหม่
6. คิดเป็นพนักงานที่ทำงานตามเจตจำนงของเจ้าของ
7. ห้ามใช้อิโมจิในผลิตภัณฑ์ ใช้ตัวอักษรหรือ CSS แทน
8. เขียนคู่มือนี้เตือนตัวเอง และส่งไฟล์ zip ที่ทำเสร็จกลับมาเสมอ
9. (รอบ 0.3.0) "สร้างความรู้" และ "ถามตัวเอง" ไม่ใช่ปุ่ม แต่เป็นระบบคิดที่ทำงานเมื่อรับข้อความและเมื่อสอนความรู้ใหม่
   การคิดต้องเกิดก่อนคำตอบ และสตรีมให้เห็นเป็นบล็อกโค้ดในแชตทีละขั้น ไม่ใช่การแสดงข้อความสำเร็จรูป

## 3. กฎเหล็ก (ห้ามละเมิด)

| กฎ | ความหมายในทางปฏิบัติ |
|---|---|
| ห้ามอิโมจิ | ไม่มีอิโมจิในหน้า, ขั้นตอนการคิด, ความรู้พื้นฐาน มีการทดสอบกันไว้ |
| ไทยล้วน | ข้อความที่โมเดลสร้างต้องผ่าน `Text.keepThai` ป้ายกำกับในบล็อกการคิดเป็นภาษาไทยล้วน |
| การคิดก่อนตอบ | ทุกคำถามที่เปิดใช้งานต้องผ่านผู้คิด (ThinkNode) ก่อนได้คำตอบ ห้ามข้ามไปตอบโดยตรง |
| ไม่กินแรม | ดัชนีค้นหาสร้างแบบขี้เกียจ กราฟเพิ่มทีละรายการเมื่อสอนต่อท้าย และสร้างใหม่ทั้งชุดเฉพาะตอนแก้ไขหรือลบรายการ, จำกัดคลัง 20,000 รายการ, ข้อสังเกต 500 รายการ |
| วัดก่อนพูด | ทุกคำกล่าวเรื่องความเร็วต้องมาจาก `npm run bench` หรือ `npm run profile` ห้ามอ้างว่า "ช้าเพราะการออกแบบดี" หรือ "เร็วเพราะการออกแบบดี" โดยไม่มีตัวเลขที่วัดได้ ถ้าช้าต้องหาคอขวดด้วย profile แล้วแก้ ไม่ใช่ปรับเป้าหมาย |
| ห้ามทำให้ logit เบลอ | เมื่อเพิ่มโมเดลประสาท การ quantize ต้องวัดความคลาดเคลื่อนเทียบกับ reference (เช่นความต่างของ logit หรือ KL) บนชุดทดสอบก่อนรวมเข้าโปรเจกต์ ห้ามปรับความแม่นเพื่อลดเวลาหรือแรมโดยไม่วัด ความเร็วที่ได้มาจากการทำให้คุณภาพเสียไม่นับเป็นความสำเร็จ |
| คอมเมนต์สำหรับพนักงาน | โค้ดที่พนักงานต้องตรวจต้องมีคอมเมนต์ภาษาไทยอธิบายเหตุผลและจุดที่ควรระวัง ไม่ใช่แค่บอกว่าโค้ดทำอะไร |
| ข้อมูลเดิมต้องไม่หาย | คีย์ localStorage ต้องคงเป็น `nino_local_ai_kb_v1` และ `nino_local_ai_set_v1` คีย์ใหม่ `nino_local_ai_mind_v1` เก็บข้อสังเกตและช่องว่างความรู้ |
| โมเดลสำรองปิดเป็นค่าเริ่มต้น | จนกว่าจะมีโมเดลที่คุณภาพผ่านเกณฑ์ ห้ามเปิดเป็นค่าเริ่มต้น |
| ส่ง zip ทุกครั้ง | เมื่อจบงานต้องสร้าง zip และส่งให้เจ้าของพร้อมสรุปการเปลี่ยนแปลง |
| พนักงานต้องมีตาและมือ | ทุก zip ต้องผ่าน `npm run play` (พนักงานขับหน้าจริงและถ่ายภาพ) แล้วเปิดดูภาพอย่างน้อย: หน้าแรก, กำลังคิด, หลังตอบ, มือถือ 375px ตรวจด้วยตาเองไม่ใช่แค่ผลตัวเลข |
| อัปเดตคู่มือ | ทุกการเปลี่ยนสถาปัตยกรรมต้องแก้เอกสารนี้ และเพิ่มในบันทึกการเปลี่ยนแปลง |

## 4. สถาปัตยกรรม

โหนดคุยกันผ่าน Bus ด้วยหัวข้อ (topic) เท่านั้น ไม่เรียกกันตรงๆ ระหว่างโหนดที่ต่อผ่านบัส

```
 UI --chat.in--> [chat] --think.begin/step/end--> UI (บล็อกกระบวนการคิด)
                   |  \--chat.out--> UI (คำตอบ)
                   v
              [thinker] --อ่าน/เขียน--> KnowledgeStore (คลัง, ข้อสังเกต, ช่องว่างความรู้)
                   |--> [retrieval]  (จับคู่ตรงตัวและคะแนนความคล้าย)
                   |--> [language]   (โมเดลสำรอง ปิดเป็นค่าเริ่มต้น)
                   |--> WordGraph    (กราฟคำ สร้างจากคลัง)
```

| โหนด (id) | ไฟล์ | บัส | หน้าที่ |
|---|---|---|---|
| chat | src/50-chat.js | รับ chat.in, ส่ง think.* และ chat.out | แยกคำสั่งสอน/ลืม/ตอบ ส่งขั้นตอนการคิดทีละขั้น |
| thinker | src/37-thinker.js | ไม่ใช้บัส (ถูกเรียกโดย chat) | ลำดับการคิด: แยกคำ, ถามตัวเอง, เชื่อม, กระตุ้น, ตัดสิน, ทบทวน |
| retrieval | src/30-retrieval.js | ไม่ใช้บัส | จับคู่ตรงตัวและคะแนนความคล้ายแบบเดิม |
| language | src/40-language.js | ไม่ใช้บัส | ช่องเสียบ adapter (ตอนนี้เป็น n-gram ทดลอง) |

หมายเหตุ: thinker, retrieval, language ไม่ได้ผูกกับบัส จึงไม่ปรากฏ in/out ใน `NINO_GRAPH.describe()`
ถ้าจะให้ผูกกับบัส ให้เพิ่ม `listen` และ `declareOutput` ในคลาสนั้น

### ลำดับการคิดของคำถาม (thinker.think)

1. start: เริ่มคิด
2. segment: แยกคำด้วย Viterbi (ต้นทุนรวมต่ำสุด) จากคลังคำพื้นฐาน + คำที่เรียนจากความรู้ที่สอน ช่วงที่ไม่รู้จักติดกันจะรวมเป็นคำเดียว
3. gap และ question: คำที่ยังไม่รู้จักถูกบันทึกเป็นช่องว่างความรู้ พร้อมขั้น "ถามตัวเอง"
4. link: เชื่อมคำที่รู้จักกับเพื่อนบ้านในกราฟ แสดงน้ำหนัก
5. activate: กระจายการกระตุ้น 2 ชั้น แล้วจัดอันดับความรู้ (candidate)
6. decide: ลำดับการตอบจากความรู้คือ ตรงตัว (exact) -> กฎเจตนา (32-intent) -> โหนดเชื่อม (33-links) -> จับคู่คล้ายกัน (ต้องถึงเกณฑ์ threshold) -> กระตุ้นความหมาย (คะแนน >= 0.6 และตรงคำอย่างน้อยครึ่งหนึ่ง) -> ประกอบเส้นทางความหมาย (path)
   เหตุผลที่กฎเจตนามาก่อนการจับคู่คล้ายกัน: การจับคู่คล้ายให้โบนัสเมื่อคำสั้นอยู่ในประโยคยาว ทำให้ "บาย" ไปอยู่ใน "สบายดีไหม" และตอบลาแทนการทักทาย
7. generate (ถ้าเปิดโมเดลสำรอง) แล้วจึง fallback

### การแยกคำ (35-lexicon.js)

- แบ่งข้อความเป็นกลุ่มอักขระก่อน (พยัญชนะ + สระ + วรรณยุกต์อยู่ด้วยกัน) แล้วหาทางแบ่งที่ต้นทุนรวมต่ำสุดด้วย Viterbi
- คำในคลังมีต้นทุน log(รวมความถี่ / ความถี่ของคำ) ส่วนกลุ่มที่ไม่รู้จักมีต้นทุนคงที่ UNK_COST = 12
- ตัดการค้นหาด้วยชุดคำนำหน้า (prefix) ผลลัพธ์เหมือนเดิมทุกประการ แต่เร็วขึ้นมาก
- เรียนเฉพาะช่วงที่ไม่รู้จัก (ยาวอย่างน้อย 2 ตัวอักษรและมีอักษรไทยหรือละติน) ไม่เรียนทั้งประโยคเป็นคำเดียว

### การสร้างกราฟ (thinker.getGraph)

- เพิ่มรายการใหม่ต่อท้าย: เรียนคำและแยกคำของรายการนั้นด้วยคลังปัจจุบัน แล้วเพิ่มเข้ากราฟทีละรายการ
- แก้ไขหรือลบรายการ: สร้างกราฟใหม่ทั้งชุด โดยเรียนตามลำดับรายการเดิม
- ทั้งสองทางให้ผลเหมือนกัน (มีเคสทดสอบ "เพิ่มความรู้ทีละรายการให้กราฟเหมือนการสร้างใหม่ทั้งชุด")
- เพื่อนบ้านของคำที่ความถี่เปลี่ยนจะถูกจัดอันดับใหม่แบบขี้เกียจ คือตอนมีการอ่านเท่านั้น ค่าที่ถูกต้องเสมอ

### โหนดเชื่อม (33-links.js)

- มีหลายโหนด แต่ละโหนดเสนอความรู้ที่อาจตรงกับคำถามพร้อมคะแนนและเหตุผล ผู้คิด (thinker._propose) ถามทุกโหนดแล้วเลือกข้อเสนอคะแนนสูงสุด
- ParaphraseLinker: ตัดคำลงท้ายที่ไม่เปลี่ยนความหมาย (ไหม มั้ย บ้าง ครับ ค่ะ ...) และรวม อย่างไร = ยังไง แล้วเทียบคีย์ความหมาย คะแนน 0.92
- SoundLinker: เทียบคีย์เสียงจาก NINO.Romanize (ไ/ใ เป็นตัวเดียวกัน ทํา/ทำ เป็นตัวเดียวกัน) เฉพาะคีย์ยาวอย่างน้อย 4 ตัว คะแนน 0.75
- กฎความปลอดภัย: เสนอเฉพาะเมื่อคีย์ตรงกับความรู้รายการเดียว ถ้าคีย์ชนกันหลายรายการจะไม่เสนอเลย (กำกวม) และคำตอบจากโหนดเชื่อมไม่ถูกนับเป็นการจับคู่ผิดของตัวปรับเกณฑ์
- ดัชนีของแต่ละโหนดสร้างใหม่เมื่อ store.version เปลี่ยน ไม่คำนวณซ้ำทุกคำถาม
- ContextLinker: คำอ้างอิงที่ไม่มีเนื้อหา เช่น "มันคืออะไร" "แล้วมันล่ะ" หมายถึงรายการที่ตอบไปล่าสุด คะแนน 0.7
  เสนอเฉพาะเมื่อประโยคเหลือแค่คำอ้างอิงกับคำถาม ถ้ามีคำอื่นติดมา (เช่น "มันเทศคืออะไร") จะไม่เสนอ
  ผู้คิดเป็นผู้จำรายการล่าสุด (thinker.context.last) จำเฉพาะคำตอบจากความรู้ ไม่จำคำทักทายหรือคำสำรอง
  คำตอบจากบริบทจะบอกชื่อเรื่องที่อ้างถึงเสมอ ("เรื่องที่เรากำลังคุยคือ ...") เพื่อไม่ให้ผู้ใช้เข้าใจว่าระบบรู้เรื่องใหม่
  ถ้ารายการนั้นถูกลืมไปแล้ว จะไม่อ้างถึงอีก
- เพิ่มโหนดใหม่: สืบทอด NINO.LinkNode แล้วคืนข้อเสนอจาก propose(text) เพิ่มเข้าในรายการ defaultLinkers

### ลำดับหลังสอน (chat._teach)

สอนคำใหม่แล้วเรียก thinker.reflect: หาคำที่อยู่ห่างสองชั้นจากคำใหม่ที่ยังไม่เชื่อมตรงกัน แล้วบันทึกเป็นข้อสังเกต
ความมั่นใจของข้อสังเกตคือผลคูณของน้ำหนักสองเส้น เก็บสูงสุด 3 รายการต่อการสอนหนึ่งครั้ง

## 5. รูปแบบไฟล์ส่งออก

เวอร์ชัน 2 (ไม่เปลี่ยนจาก 0.2.0 แค่เพิ่มฟิลด์ insights ที่ตัวนำเข้าเพิกเฉย):
```json
{ "format": "nino-knowledge", "version": 2, "exportedAt": "...", "count": 0,
  "knowledge": [ { "q": "...", "a": "...", "hits": 0, "created": 0, "updated": 0 } ],
  "insights": [ { "text": "...", "conf": 0.0, "a": "...", "b": "...", "via": "..." } ] }
```
ตัวนำเข้ารองรับเวอร์ชัน 1 (array หรือ `{knowledge}`) และชื่อฟิลด์ `q/a`, `question/answer`, `key/value`
ห้ามทำให้ไฟล์เวอร์ชัน 1 นำเข้าไม่ได้

## 6. วิธีต่อยอด

### เพิ่มโหนดใหม่
1. สร้างไฟล์ใน src/ ในรูปแบบ IIFE เดียวกับไฟล์อื่น สืบทอด `NINO.Node`
2. ใช้ `this.listen(topic, fn)` สำหรับรับ และ `this.declareOutput(topic)` สำหรับส่ง
3. ลงทะเบียนใน ui/app.js ด้วย `graph.add(new ...)` รหัสต้องไม่ซ้ำ
4. เพิ่มไฟล์ใน CORE_FILES ของ tests/run-tests.js ตามลำดับที่ต้องโหลด แล้วเขียนเคสทดสอบ
5. เพิ่มไฟล์ใน index.html ตามลำดับ (ต้องมาหลัง 00-core และไฟล์ที่ถูกเรียกใช้ตอนโหลด)

### เพิ่มกฎการคิด
แก้ที่ `thinker.think` หรือ `thinker.reflect` ทุกขั้นที่ต้องการให้ผู้ใช้เห็นต้องใช้ `yield step(kind, text)`
ชนิดขั้น (kind) ต้องมีป้ายใน LABELS ของ ui/view.js ไม่เช่นนั้นจะแสดงว่า "คิด"

### เสียบโมเดลใหม่ (adapter)
adapter ต้องมี `id`, `ready()`, `train(texts)`, `generate(prompt, rng, maxChars)` และคืนค่า string หรือ null
ลงทะเบียนด้วย `language.use(adapter)` ผลลัพธ์ทุกครั้งต้องผ่าน `Text.keepThai`
ก่อนรวมโมเดลประสาท ให้เพิ่มรายการใน models/manifest.json และตรวจขนาดแรม

## 8. ข้อจำกัดที่ต้องบอกตรงๆ

- การคิดเป็นกฎเหนือกราฟคำที่เขียนเอง (heuristic) ไม่ใช่การอนุมานของโมเดลประสาท
  ระบบประกอบความรู้ที่มีเป็นคำตอบใหม่ได้เมื่อเส้นทางความหมายชัดเจน แต่จะไม่สร้างภาษาไหลลื่นแบบ LLM
- การประกอบคำตอบจากเส้นทาง (composed) ใช้ความรู้บนเส้นทางเป็นคำตอบ อาจไม่ตรงคำถามเสมอไป
  ระบบติดป้ายว่า "คิดต่อจากเส้นทาง" เพื่อให้ผู้ใช้ตรวจได้
- โมเดลภาษาในเวอร์ชันนี้ (ngram-th) เป็นของทดลอง และปิดเป็นค่าเริ่มต้น
- น้ำหนักโมเดลภาษาไทยแบบประสาทยังไม่ได้รวมอยู่ เพราะขนาดไฟล์และแรม
- การแยกคำขึ้นกับคลังคำพื้นฐานขนาดเล็ก (ราว 200 คำ) และคำที่เรียนจากความรู้ที่สอน คำที่ไม่อยู่ในคลังจะถูกตัดเป็นช่วงอักขระ
- ความจำอยู่ใน localStorage ประมาณ 5 ถึง 10 เมกะไบต์ต่อโดเมน
- ยังไม่มีการซิงก์ข้ามเครื่องและยังไม่มีบัญชีผู้ใช้

## 9. แผนระยะยาว (มองการณ์ไกล)

1. ขยายคลังคำพื้นฐานและแยกคำด้วยวิธีที่ดีกว่า (เช่นตารางความถี่หรือโมเดลแยกคำ) โดยไม่เพิ่มแรมมาก
2. ย้ายคลังไป IndexedDB และแบ่งกราฟเป็นส่วนย่อยที่โหลดเมื่อจำเป็น
3. เลือกและทดสอบโมเดลภาษาไทยแบบประสาทขนาดเล็กที่ quantize แล้ว วัดแรมและความเร็วบนเครื่องจริง
4. ผูกโมเดลประสาทเป็น adapter และเปรียบเทียบคุณภาพกับ n-gram บนชุดทดสอบภาษาไทย
5. ให้ผู้คิดตรวจข้อสังเกตกับผู้ใช้ก่อนนำไปใช้ตอบ (ยืนยันหรือปฏิเสธข้อสังเกต) เพื่อลดข้อผิดพลาดสะสม
6. ชั้นความเป็นส่วนตัว: ข้อมูลอยู่ในเครื่องเท่านั้น และการส่งออกเข้ารหัสได้
7. โครงสร้างองค์กร: ระบบโมดูล ทะเบียนโมเดล เวอร์ชันความรู้ และตัววัดคุณภาพต่อเนื่อง

คอขวดจาก profile (เวลาใช้เองรวมทุกขนาด) หลังแก้แล้ว:
1. การเพิ่มคู่คำเข้ากราฟตอนสร้างทั้งชุด (_add) ราว 19%
2. การแยกคำด้วย Viterbi (segmentChunk และ clusterEnds) ราว 22%

## 12. โน้ตจากเจ้าของ (ข้อควรรู้สำหรับพนักงาน)

บันทึกจากไฟล์ที่เจ้าของแนบมา สรุปและจดไว้ตามเดิม ข้อที่ขัดกันจดทั้งสองด้านและรอเจ้าของยืนยัน ห้ามเลือกเองแล้วลบอีกด้าน

ความเป็นตัวตนของระบบ
- ระบบนี้ "ไม่ฉลาดโดยเจตนา" ความซื่อสัตย์ของอัลกอริทึมคือจุดขาย ไม่ใช่ข้อบกพร่อง
- fallback บ่อยคือความซื่อสัตย์ ไม่ใช่ bug
- exact match ที่ได้ 100% คือการจำได้ ไม่ใช่ bug
- threshold ที่ทำให้ตอบน้อยคือความมั่นใจ ไม่ใช่ bug
- ระบบยังไม่รู้ความหมายเชิงลึก (semantic) คือข้อจำกัดที่ยอมรับได้ แต่พัฒนาต่อได้
- single-file .zip คือจุดยืนของผลิตภัณฑ์ ไม่ใช่หนี้ทางเทคนิค

หลักที่ต้องยึดเมื่อแก้โค้ด
- ระบบพัฒนาได้และต้องฉลาดขึ้น แม่นขึ้น นั่นคือเป้าหมายปกติ
- เส้นตายคือความซื่อสัตย์: ไม่รู้ = บอกว่าไม่รู้ ห้ามเดามั่วเพื่อให้ดูฉลาด
- fallback ไม่ใช่ความล้มเหลว เป็นคำเชิญให้ผู้ใช้สอน
- "ทำให้ตัวเลขดูดี" ไม่เท่ากับ "ทำให้ผลิตภัณฑ์ดีขึ้น"
- "ลด fallback" ทำได้ก็ต่อเมื่อระบบฉลาดขึ้นจริง ไม่ใช่เพราะเปลี่ยนเกณฑ์ให้ตอบมั่วมากขึ้น
- "เพิ่มความแม่นยำ" ต่างจาก "การแกล้งรู้" ต้องแยกให้ชัด

ข้อที่ขัดกัน (รอเจ้าของยืนยัน)
- LM, embedding, build step: ฉบับหนึ่งเขียนว่า "ห้ามเพิ่ม" อีกฉบับเขียนว่า "เพิ่มได้ถ้าจำเป็น แต่ต้องชั่งน้ำหนักกับ zip ที่เปิดใช้ทันที"
  สถานะปัจจุบัน: ไม่มี LM หรือ embedding ในระบบ มีเพียง n-gram ทดลองที่ปิดเป็นค่าเริ่มต้น
- threshold 0.34: ฉบับหนึ่งเขียนว่า "ห้าม tune" อีกฉบับเขียนว่า "ปรับได้ถ้าทำให้ฟังภาษาไทยดีขึ้นจริง"
  สถานะปัจจุบัน: ค่าเริ่มต้นยังเป็น 0.34 ไม่มีการปรับ
- รายการ "bug ที่ห้ามแตะ" ข้อสุดท้ายเขียนว่า "bug ที่ทำให้ระบบแกล้งรู้ตอนที่ไม่รู้" ซึ่งขัดกับเส้นตายความซื่อสัตย์
  ตีความไว้ว่าเป็นการพิมพ์ผิด และ "แกล้งรู้" คือสิ่งที่ต้องแก้ รอเจ้าของยืนยัน

คำตอบของเจ้าของ (รอบ 0.6.0)
- ให้ทั้งอัลกอริทึมแบบไปป์ไลน์และแบบคู่ขนาน: ทำทั้งสองแบบ (ไปป์ไลน์คือ 46-textpipe.js และคลาสมารยาท, คู่ขนานคือ 32-intent.js)

★ 46. โหมด 1 ใช้ความรู้ของมิ้ม 100%: ทุกคำตอบของโหมด 1 มาจากคลังของมิ้มเท่านั้น มี 2 ทาง (1) โมเดลเรียบเรียงได้เมื่อคู่ตัวอักษรอย่างน้อย 95% อยู่ในความรู้ที่ให้ไป (แหล่ง 'model') (2) ถ้าโมเดลตอบไม่ผ่านหรือพัง มิ้มใช้คำที่สอนไว้ในคลังโดยตรง ไม่ดัดแปลง (แหล่ง 'verbatim') และใช้ได้เฉพาะเมื่อคะแนนค้นอย่างน้อย 0.6 และแกนของคำถามอยู่ในคำถามของรายการนั้น (เช่น "ปัญญาคืออะไร" ไม่ใช้คำตอบของ "ปัญญาประดิษฐ์คืออะไร") ถ้าไม่มีทั้งสองทาง มิ้มตอบว่ายังไม่รู้ ไม่มีกรณีที่คำตอบมาจากนอกคลัง ป้ายบอกที่มาอยู่ใต้คำตอบ การสลับแหล่งไม่เขียนทับความรู้ของมิ้ม
★ 47. ชั้นโค้ดของโมเดลในเครื่อง (checkCode ใน js/local-llm.js): ทุกคำตอบจากโมเดลในเครื่องถูกตรวจก่อนส่ง ต้องไม่บอกชื่อโมเดลหรือบริษัทอื่น บล็อก ``` ต้องปิดครบ (คำตอบที่ถูกตัดกลางคันไม่ผ่าน) บล็อก js ต้องผ่านการตรวจไวยากรณ์ด้วย new Function (ไม่รันโค้ด) บล็อก json ต้อง parse ได้ ตรวจข้อความดิบที่ตัด <think> แล้ว ก่อนลบรั้วโค้ดที่ cleanResponse ทำ ทุกการเรียกมีกติกาการตอบ (CODE_RULES) ต่อท้ายคำสั่งระบบ ตรวจด้วย tools/test/local-code-guard.test.js และ tools/test/local-llm.test.js
★ 48. โหมด 1 ส่งเสริมการเติบโตของมิ้มด้วยการยืนยันของผู้ใช้เท่านั้น: เมื่อคำตอบของโหมด 1 ออกมาแล้ว ฟองคำตอบมีปุ่ม "ใช่ ตอบตรง ให้มิ้มจำ" ถ้ากด มิ้มจำคำถามที่ผู้ใช้ถาม โดยใช้คำตอบที่สอนไว้เดิมของรายการที่ตรง (ไม่ใช่ข้อความของโมเดล) ผ่าน Learn.teach ครั้งหน้าคำถามรูปนี้มิ้มตอบเองได้โดยไม่เรียกโมเดล ไม่มีการจำอัตโนมัติ และไม่มีข้อความจากโมเดลเข้าคลัง ตรวจด้วย tools/test/mim-llm-popup.test.js (ส่วน 2b)
★ 49. ทดสอบการเล่นจริงด้วยคำถามทั่วไป (tests/play-test.js) และกติกาที่ได้จากการเล่น: (1) คำถาม "กี่/เท่าไร" ต้องได้คำตอบที่มีตัวเลขเสมอ และในเส้นทางความหมาย (ประกอบคำ) คำที่พิมพ์ทุกคำต้องอยู่ในรายการที่ตอบ (2) "X ทำยังไง" ก็ต้องมีคำเฉพาะของ X ในรายการ (ไม่ตอบผัดไทยเมื่อถามข้าวผัด) (3) ตัวตนของผู้ช่วยตอบตามแอป NINO ไม่บอกชื่อบริษัทอื่น (4) กฎเจตนาใหม่: ทักทายก่อนนอน อากาศร้อน ไม่ชอบ (5) คำถามที่มิ้มตอบไม่ได้ถูกจดทั้งข้อไว้ที่คลัง (สูงสุด 30 ข้อ เก็บข้ามการโหลดใหม่ และออกจากรายการเมื่อสอนแล้ว) ฟองคำตอบที่ตอบไม่ได้มีปุ่ม "สอนเรื่องนี้" และช่องสอนแสดงรายการล่าสุดให้กดสอนต่อได้ (6) การค้นแบบคล้ายกัน (fuzzy) ไม่ใช้การตรวจการครอบคลุมคำ เพราะจะตัดคำถามที่พูดต่างจากความรู้ออกมาก (วัดแล้ว DEV และ HELD ลดลงมาก)
★ 50. คำตอบแบบ "เรื่องใกล้เคียง" (kind = related): เมื่อไม่มีคำตอบตรง แต่มีความรู้ที่หายาก (อยู่ในรายการไม่เกิน 2 รายการ) ที่มีคำเฉพาะร่วมกับคำถาม มิ้มจะบอกตรงๆ ว่า "ยังไม่มีคำตอบตรงเรื่อง … แต่เรื่องใกล้เคียงที่ฉันรู้คือ …" แล้วตามด้วยคำตอบของเรื่องนั้น ไม่ปล่อยให้เป็นแค่ "ไม่รู้" และไม่แสดงเป็นคำตอบของคำถาม ถ้าไม่มีคำร่วมที่หายากเลย มิ้มยังตอบว่ายังไม่รู้ตามเดิม (ดู ★49 ข้อ 2 สำหรับกฎเดิมของการประกอบคำ) ฟองแบบนี้มีปุ่ม "สอนเรื่องนี้" และคำถามถูกจดในรายการที่ยังไม่รู้เหมือนคำตอบว่าไม่รู้
★ 51. ประตูตรวจ CI ไม่ใช้เบราว์เซอร์ (tools/ci-gate.sh): ใช้ตอนซิปถูก unpack ใน android/ci/unpack-zip.yml รันทุกขั้น (ซิปครบไฟล์ check --strict NOW packs และเทสต์ node ทั้งหมด รวม eval --gate) แล้วสรุปผล ซิปที่ไม่มีสคริปต์นี้ถือเป็นซิปรุ่นเก่า ไม่ commit ขั้นที่ต้องใช้เบราว์เซอร์ยังรันด้วย verify-all.sh ในเครื่องก่อนส่งซิปเสมอ

★ 52. ค้นเว็บหาคำตอบ: เมื่อมิ้มตอบไม่ได้ ฟองจะมีปุ่ม "ค้นเว็บหาคำตอบ" (แสดงเฉพาะตอนเปิดสวิตช์ค้นเว็บ) ผลที่ได้ไม่เข้าความรู้ทันที มิ้มจะพักเป็น "ผู้สมัคร" และแสดงในถาด "รอยืนยันจากเว็บ" ในช่องสอน (กดปุ่มคำถามเพื่อเปิด) ทุกข้อมีที่มาและระดับความน่าเชื่อถือ กด "ยืนยัน จำไว้" เพื่อให้มิ้มจำ หรือ "ทิ้ง" ถ้าไม่ตรง ถ้าคำถามนั้นมีความรู้เดิมแล้ว มิ้มจะไม่เขียนทับ ก่อนยืนยันมิ้มไม่ตอบเรื่องนั้นจากผลค้นเว็บ โหมด 1 ยังตอบได้เฉพาะจากความรู้ของมิ้มที่ยืนยันแล้วเท่านั้น
