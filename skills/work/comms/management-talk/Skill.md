# management-talk
เมื่อผู้ใช้ขอเขียนให้ผู้บริหาร/PM อ่าน: เรียบเรียงงานวิศวกรเป็นคอมเมนต์ตั๋ว สแล็ก สแตนด์อัป อีเมล หรือประเด็นประชุม
## เมื่อไหร่
- ผู้ใช้สั่ง "เขียนให้ผู้บริหาร/หัวหน้า/PM" "ทำให้เทคนิคน้อยลง" "สรุปสถานะ/exec summary" "ขอเวอร์ชันสแล็ก/อีเมล/สแตนด์อัป/ประเด็นประชุม" จากงานวิศวกรรมที่มีอยู่แล้ว
- ไม่ใช่สำหรับการตลาด การเงิน ลูกค้าทั่วไป หรืออธิบายให้เด็กเข้าใจ → บอกและยืนยันก่อนทำ
- ช่องทางไม่ชัด → ถามคำเดียว: "คอมเมนต์ตั๋ว, สแล็ก, สแตนด์อัป หรืออีเมล?" แล้วหยุดรอ
## ผู้อ่าน
คนในองค์กรวิศวกรรมที่ไม่อ่านโค้ด: รู้จักชื่อผลิตภัณฑ์/เฟรมเวิร์ก/รหัสตั๋ว/เลข PR อยากรู้ ตอนนี้เป็นอย่างไร กระทบลูกค้าอย่างไร ใครดูแล ต่อไปทำอะไร ไม่อยากรู้กลไกระดับฟังก์ชัน
## น้ำเสียง
- เก็บ: ชื่อผลิตภัณฑ์/เฟรมเวิร์ก/คอมโพเนนต์ที่ทีมเป็นเจ้าของ รหัสตั๋ว เลข PR ชื่อลูกค้า/เวิร์กโหลด
- ตัด: ชื่อฟังก์ชัน path ไฟล์ ฟิลด์ struct sha ตัวแปรสภาพแวดล้อม เลขบรรทัด
- แปลกลไกเป็นเหตุ-ผล 1–2 ประโยคแบบไม่โกหก (race ยังเป็น race, regression ยังเป็น regression) · อย่าตัดศัพท์ระดับแนวคิดที่ผู้อ่านคุ้น (race condition, synchronization, workaround) จนดูดูถูก
- ประโยคกระทำ ประธานชัด ย่อหน้าสั้น · เขียนเป็นไทยตามผู้ใช้ ศัพท์เทคนิคคงอังกฤษ
- เลี่ยง: คำกั้นที่ไม่ใช่การกั้นจริง (น่าจะ/ดูเหมือน) · ย้ำสิ่งที่รู้อยู่แล้ว · สอนผู้อ่านว่าควรจัดลำดับอะไร (ให้ข้อเท็จจริง ให้เขาตัดสินเอง) · รายละเอียดวิธีดีบัก (ยกเว้นเมื่อ "กระบวนการ" คือเรื่องเล่า ให้เหลือประโยคเดียวแบบบทเรียน)
## รูปตามช่องทาง (เนื้อเดียวกัน เปลือกต่างกัน)
- คอมเมนต์ตั๋ว/รายงานสถานะ: บล็อกเต็ม ป้ายตัวหนา เรียงตามที่สำคัญกับเรื่องนี้: สถานะ/สรุป (บรรทัดเดียวอ่านแค่นี้ก็พอ) · ผลกระทบ (ใคร เห็นอะไร ศัพท์ลูกค้า/เวิร์กโหลด) · อะไรพัง · ทำไมหลุดมา (เมื่อผู้อ่านจะถามอยู่ดี) · ผู้รับผิดชอบ (คน+ทีม+ลิงก์เดียว) · ขั้นต่อไป (เรียงลำดับ) · วิธีเลี่ยงชั่วคราว · ความเสี่ยง (เฉพาะที่จริง)
- สแล็ก: ข้อความเดียว ไม่เป็นกำแพง · บรรทัดแรกตัวหนาสรุป · 2–4 บูลเล็ต (ผลกระทบ ผู้ดูแล+ลิงก์ ก้าวต่อไป) · ลิงก์เดียว · ไม่ทักทาย ไม่ลงท้าย · ตอบในเธรดตัดสรุปเปิดด้วยคำตอบเลย · ความยาว ≲ 80 คำ (เธรด ≲ 40)
- สแตนด์อัป: 1–3 บรรทัด รูป "<สถานะ> <เรื่อง> <ผู้ดูแลถ้าไม่ใช่เรา> <ก้าวต่อไป>" ขึ้นต้นด้วยกริยา ไม่มีบูลเล็ตหรือป้าย
- อีเมล: หัวเรื่อง = สรุปเป็นวลีนาม · ทักทายตามระดับผู้รับ · เนื้อ 2–3 ย่อหน้า (ไม่ใช้ป้ายตัวหนา) · ปิดด้วยสิ่งที่ต้องการให้ผู้รับตัดสินใจ ถ้าไม่มีลงชื่อธรรมดา
- ประเด็นประชุม: บูลเล็ตสั้นตามลำดับที่จะพูด ใส่ตัวเลข/รหัสที่จะอ้างไว้ในบูลเล็ตเอง
## แหล่งข้อมูล
ข้อความที่ผู้ใช้วาง หรือเนื้อหาวิศวกรรมที่เพิ่งคุยกันในแชท · ไม่คลุมเครือแหล่ง → ถามหนึ่งคำถามแล้วหยุด (NINO ไม่มีเครื่องมือดึงตั๋วอัตโนมัติ)
## ส่งงาน
- พิมพ์ร่างเป็นบล็อกเดียวในรูปที่ช่องทางนั้นแสดง แล้วให้ผู้ใช้คัดลอกไปโพสต์เอง · ห้ามโพสต์ไปที่ไหนเอง
- แก้ครั้งที่ 1 ปกติ ครั้งที่ 3 คือสัญญาณว่าเข้าใจผู้อ่านผิด ถามว่าตรงไหนที่ฉันเข้าใจผิด
## กฎ
- ห้ามแต่งข้อเท็จจริงให้เรียบร้อย: ต้นฉบับบอก "ยังไม่รู้สาเหตุ" ต้องเขียนว่ายังไม่รู้สาเหตุ ห้ามยกสมมติฐานเป็นข้อค้นพบ
- ห้ามตัดรหัสตั๋ว เลข PR ชื่อลูกค้า/เวิร์กโหลด (สะพานให้ตามงานได้) · ห้ามแต่งชื่อผู้รับผิดชอบ ถ้าต้นฉบับไม่บอกให้ถาม
- ไม่เสนอแนะเชิงโน้มน้าว นี่คือรายงานสถานะ ไม่ใช่บันทึกขอมติ
- ต้นฉบับเต็มพร้อมตัวอย่างสามช่องทาง: docs.md · คู่กับ post-mortem (post-mortem ถือความจริงด้านวิศวกรรม สกิลนี้เรียบเรียงขึ้นไป)
