# pointer-audit
เมื่อสกิลถูกเรียกพลาด/ไม่ถูกเรียก หรือเพิ่งเขียนสกิลใหม่: ตรวจ pointer ให้คม แล้วแก้ที่ pointer ไม่ใช่ที่เนื้อสกิล
## หลักคิด
- pointer = ข้อความในบริบทที่ชี้ไปหาเนื้อหาอีกที่ และบอกว่า "เมื่อไหร่ควรไปดึง": บรรทัดที่ 2 ของ Skill.md ที่ขึ้นสารบัญ · บรรทัด "→ skill_read X" ใน Skill.md ราก · ประตูใน skills/_gates.md
- โมเดลตัดสินใจตามถ้อยคำของ pointer ไม่ใช่ตามเนื้อหาปลายทาง → pointer อ่อน + ปลายทางจำเป็น = บั๊กความแปรปรวน (รันแต่ละครั้งทำไม่เหมือนกัน)
- อย่าแก้ที่ปลายทาง แก้ที่ pointer
## ขั้นตอน (ตามลำดับ ห้ามข้าม)
1. ตรวจ: lib_health (ผู้ใช้พิมพ์ `nino lib` ในเทอร์มินัลได้) อ่านรายการสีแดง/สีเหลือง — pointer ที่ติดธงคือผู้ต้องสงสัย
2. Sharpen: เขียนบรรทัดที่ 2 ใหม่ ขึ้นต้นด้วย เมื่อ/ก่อน/หลัง/ถ้า + สิ่งที่สังเกตได้ (ชื่อเครื่องมือ ข้อความ error จำนวนไฟล์) ใช้คำเฉพาะที่ไม่ซ้ำเล่มอื่น ไม่เกิน 140 ตัวอักษร
3. Front-load: คำที่ชี้ตัวตนที่สุดต้องอยู่ต้นประโยค โมเดลอ่านต้นประโยคก่อน
4. Branch isolation: เล่มที่ชั้นเดียวกันหรือดูคล้ายกัน → เพิ่ม 1 บรรทัดใน skills/_gates.md: หัวข้อ | เงื่อนไข → เล่ม ; เงื่อนไข → เล่ม
5. Inline (ทางสุดท้าย): ถ้ายังพลาด ย้ายคำสั่งสำคัญมาอยู่ติดกับจุดที่เรียก (ขั้นตอนใน Skill.md ราก) ให้ "เรียก" กับ "ทำ" อยู่ใกล้กัน
6. Surgical cut: ถ้ายังแปรปรวน เปลี่ยนเป็น user-invoked — ผู้ใช้พิมพ์ /ชื่อเล่ม ในแชท แอปแนบเล่มให้เอง ไม่ต้องให้โมเดลเลือก — และย่อ Skill.md ให้เล็กสุด
7. ตรวจซ้ำให้เป็นสีเขียว แล้วจด skill_note kind ได้ผล ว่า pointer เดิมอ่อนเพราะอะไร
## กฎ
- ห้ามขึ้นต้นด้วยคำนามกว้าง (วิธี/ปัญหา/กฎ/เรื่อง) หรือคำคลุมเครือ (ต่างๆ/ทั่วไป/ที่เกี่ยวข้อง/ถ้าจำเป็น)
- เล็กลงดีกว่า: Skill.md เกิน 200 บรรทัดเหลือง เกิน 500 แดง ย้ายส่วนอ้างอิงไป docs.md (progressive disclosure) แต่ห้ามซ่อนสิ่งที่ทุกสาขาต้องใช้
- ผลตรวจเป็นแค่ธง: ตัดสินใจเองว่าคำเตือนไหนจริง
- ต้นฉบับโปรโตคอลเต็ม: docs.md
