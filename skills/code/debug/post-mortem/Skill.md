# post-mortem
หลังแก้บั๊กจบและพิสูจน์ผ่านแล้ว: เขียนบันทึกสาเหตุ กลไก วิธีแก้ การพิสูจน์ และทำไมหลุดมา
## เมื่อไหร่
- หลังแก้บั๊กจบจริงเท่านั้น (ผู้ใช้สั่ง "สรุปสาเหตุ/post-mortem/RCA" หรือ NINO เสนอเองหลังดีบักจบ)
- ไม่ใช้: บั๊กยังไม่จบ/ยังไม่ได้พิสูจน์ · เหตุขัดข้องที่ผู้ใช้ปลายทางเจอวงกว้าง (ต้องใช้รายงานเหตุการณ์แยก) · แก้ typo/บรรทัดเดียวที่ข้อความ commit พอแล้ว
## ต้องครบ 4 ข้อก่อนเขียนสักบรรทัด (ขาดข้อไหนบอกว่าขาดอะไรแล้วหยุด)
1. มีสูตรทำซ้ำที่เชื่อถือได้ 2. รู้สาเหตุแล้ว (ไม่ใช่สมมติฐาน) 3. รู้ว่าแก้ที่ไหน (sha จาก gh_commit / ไฟล์+ฟังก์ชัน) 4. พิสูจน์แล้วว่าสูตรเดิมผ่าน (ถ้าเป็นเว็บล้วน บอกว่าไม่ได้ลองบน APK)
## โครงสร้าง (บังคับ: สรุป · สาเหตุ · วิธีแก้ · การพิสูจน์)
1. สรุป — ย่อหน้าเดียว อะไรพัง (ภาษาผู้ใช้) + แก้ด้วยอะไรหนึ่งประโยค + เวอร์ชัน/sha
2. อาการ — ข้อความ error/พฤติกรรมจริง ตัวระบุเป๊ะ ไม่ถอดความ
3. สาเหตุ — กลไกจริง ใส่ชื่อไฟล์ ชื่อฟังก์ชัน เงื่อนไข sha ที่ต้นเหตุ ไล่ห่วงโซ่ตั้งแต่ต้นจนจบ
4. ทำไมจึงเกิดอาการนั้น — โยงสาเหตุไปอาการ (มักห่างกันหลายชั้น)
5. วิธีแก้ — แก้อะไร ทำไมแก้ที่ต้นเหตุ ไม่ใช่ซ่อนอาการ · ถ้ามีวิธีแก้เดิมที่ปิดอาการ บอกว่าผิดตรงไหน
6. หาเจอได้อย่างไร — สูตรที่ทำให้ซ้ำได้ เครื่องมือที่ไขได้ สมมติฐานที่ตกไป (บรรทัดละข้อ + เหตุผล) การทดลองเดียวที่ชี้ขาด (ดึงจากสมุดเบาะแสของ debug-mantra)
7. ทำไมหลุดมา — เลือกเหตุจริง: ไม่มีเทสต์ครอบ / โค้ดถูกตอนเขียนแต่ถูกแก้ภายหลัง / ยังไม่มีเคสจริงมาถึงจุดนี้ / แก้ครั้งก่อนปิดอาการ / รีวิวพลาด · ไม่มีเหตุผลดี ก็บอกตรงๆ · เป็นกลาง ไม่โทษคน
8. การพิสูจน์ — เทสต์/เคสที่ผ่านแล้ว ชื่อชัด · ลองครอบคลุมแค่ไหน บอกตรงๆ (ลองแค่ 1 แบบก็เขียนว่า 1 แบบ)
9. งานต่อ — แต่ละข้อ: อะไร + ใคร + ที่ติดตาม (เพิ่มเทสต์ที่ไหน แก้ CI ช่องไหน อัปเดตเอกสารไหน) · ไม่มี = "ไม่มี — แก้เพียงพอแล้ว" ห้ามแต่งให้ดูครบ
## ส่งผลลัพธ์
- ค่าเริ่มต้น: พิมพ์เป็นบล็อกเดียวในแชท แล้วจด 1 บรรทัดด้วย skill_note ที่เล่มที่เกี่ยว (kind: ผิด) ว่า "อาการ → สาเหตุ → ที่แก้"
- ลงรีโปเป็นไฟล์ (docs/postmortems/วันที่-ชื่อ.md ด้วย gh_create) เฉพาะเมื่อผู้ใช้สั่ง ไม่โพสต์ที่อื่นเอง
- เสนอต่อว่าจะให้ยกระดับเป็นภาษาผู้บริหารด้วย management-talk ไหม ไม่ทำเอง
## กฎ
- ห้ามแต่งสาเหตุ ผู้รับผิดชอบ หลักฐานการทดสอบ หรืองานต่อ ถ้าไม่มีข้อมูลให้ถาม
- ห้ามตัดตัวระบุโค้ดออก (มันคือดัชนีให้คนหลังเสิร์ชกลับมา) · ห้ามใช้คำคลุมเครือ "น่าจะ/อาจจะ" ในบรรทัดที่เป็นข้อเท็จจริง
- แก้ร่างเกิน 3 รอบ ถามว่าส่วนไหนผิดแทนการแก้มั่ว
- ต้นฉบับเต็มพร้อมตัวอย่าง: docs.md
